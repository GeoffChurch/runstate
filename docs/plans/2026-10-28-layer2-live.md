> **For agentic workers:** executed subagent-driven, in the batches below. Steps use checkbox (`- [ ]`) syntax
> for tracking.

**Execution** (owner, 2026-10-30). A task is a **commit unit**: green alone, bisectable, one reviewable diff.
A batch is a **dispatch unit**: one fresh implementer works through its tasks in order, committing and
pushing after each and ticking its checkboxes, so a fresh agent can resume from the tree if one dies or
compacts. Then a two-stage review of the batch (spec compliance, then code quality) reads it commit by commit.
- **Serial, Opus at most:** one agent at a time, never Fable.
- **No batch crosses a stage boundary,** and nothing crosses the cutover, which needs every earlier task's
  `Ported:` and `Dropped:` lists.
- **Independence where it is the point:** batch 9's implementer is a fresh agent that built none of the live
  layer, so the guide tests whether the spec stands alone and the property test's generator does not share
  the Worker's assumptions.
- **Batch 10 has no implementer:** the controller runs Tasks 19–20's scripts itself, and a reviewer checks
  them.

**Goal:** Implement the live layer of `docs/specs/commits-and-lineage.md` (revision 2, approved 2026-10-28,
ruling 12a): the wire of §3, the Worker of §4, the reads of §5, the checkpoint recipe of §6, the death reports
and the Postgres session probe of §3 and §11, §8's in-repo examples, §9's interop tests, §10's tests and §11's
ripple. Then flip the format: register 0.4.0 and the 0.3.0 → 0.4.0 step, set `LOG_FORMAT = "0.4.0"`, and bump
the package to `0.4.0.dev0`, in the plan's last commit.

**Architecture:**
- **Stage 1, the ground.** Four changes in place, none of which changes a log's records:
  - the retained steps' tests and the corpus runner stop using the 0.3.0 `Worker` and `observables`, which this
    plan replaces, by freezing what they took from them;
  - the memory backend reads a tail as a slice and keeps a per-topic index, and every backend gains the
    substrate-contract test;
  - a format's layout holds its tables on both backends, and every writer takes the tables of the format it
    writes;
  - the Postgres channel gains the session probe: a fresh key per connection taken before its first write, a
    stamp on every row, `synchronous_commit` set and `fsync = off` refused.
- **Stages 2 to 5, the staged live layer.** The 0.4.0 live layer is built beside the 0.3.0 one, in a staging
  package `runstate/_next/` that mirrors the final layout, with its tests in `tests/test_next_*.py`. The 0.3.0
  modules and their tests run unchanged meanwhile, so every commit passes the hook.
  - **Why staged.** The Worker writes the records every read and every test reads. So switching the Worker in
    place forces the payloads, the reads, the Watcher, `ensure`, the launchers and about 400 tests to switch in
    the same commit. The 0.3.0 cutover did that across four commits with `--no-verify`, which this plan may not
    do (brief, ruling 8). Staging splits the work into tasks one implementer can finish and one reviewer can
    judge, each green.
  - **What it costs.** Two copies of the live layer exist on the branch until Task 19, and Task 19 is a large
    but mechanical commit. Master never sees either, since the branch merges whole.
  - **Stage 2** writes the 0.4.0 vocabulary: the bodies, `Topic`, the coordinate types and the condition
    algebra over counts.
  - **Stage 3** moves `runstate/lineage.py`'s provisional reads into their staged homes, adds the remaining
    reads, the claim plane and the incremental folds.
  - **Stage 4** writes the death-report helpers and launchers, then the Worker in four tasks, then the
    checkpoint recipe.
  - **Stage 5** writes `ensure`, the Watcher, the public surface, the schema scenario, the implementers guide
    and the order-independence property.
- **Stage 6, the cutover.** One commit moves `runstate/_next/` over the 0.3.0 modules and renames the staged
  tests over the old ones. A second removes the 0.3.0 schemas from `protocol/`. From here the live layer writes
  0.4.0 shapes under 0.3.0's address, which only this branch ever does.
- **Stage 7, the edges and the flip.** The examples, the documents, then the flip.

**Tech Stack:** Python 3.12, sqlite3, psycopg 3 (the optional `[postgres]` extra), jsonschema (tests only),
pytest, mypy `--strict`, black. No new runtime dependency.

## Review Focus

Five inputs the spec implies, that no §10 test exercises, and that are the likeliest to bite a user. Each has a
test, added to the task that owns its code.

1. **Two `emit`s of one name in one iteration are two elements** (§2, "Order within a node"). A consumer porting
   from `value_series`, where a (name, step) cell held one value, will expect the second to replace the first.
   `test_two_emits_of_one_name_in_one_iteration_are_two_elements` (Task 10a): `prefix_len` counts 2, `series`
   holds both in emit order, and `last_element` is the second.
2. **A target naming a declared source never counts** (§5: "a name that was a source throughout counts 0"). A
   worker that `set`s `loss` where it should `emit` it would drive forever: its count stays 0 while each chunk
   commits, so no `NoProgressError` fires. `test_steps_refuses_a_target_naming_a_declared_source` (Task 10b) and
   `test_ensure_refuses_a_target_its_drives_claim_declares_a_source` (Task 14), per open question 1.
3. **A drain whose compare-and-append loses re-drains, and registers and binds exactly once** (§4, "A drain").
   A concurrent control writer makes the `bound` CAS fail; an implementation that registered the lease before
   the CAS, or that writes a second `bound` on the retry, serves a lease the log does not bind.
   `test_a_drain_that_loses_its_cas_binds_and_registers_a_lease_exactly_once` (Task 12), with a channel that
   appends a stop just before the worker's first `bound` CAS.
4. **A save policy that raises after its node landed** (§6, "A save that raises"). A disk-full checkpoint write
   raises at either moment the Worker saves, and the node stands either way; nothing records the failed save.
   - **After a commit,** it raises out of `commit()`: `__exit__` must write an errored, torn exit whose `parent`
     is that node, and the node stays extendable.
     `test_a_save_policy_that_raises_leaves_its_node_committed_and_the_exit_torn` (Task 11).
   - **After an extendable exit,** it raises out of `stopped()`: the exit stands with its own verdict, nothing
     more is written, and the next claim, following the recipe, resumes from an older checkpoint and branches.
     An implementation tempted to catch it, rewrite the exit, or save before the exit's CAS breaks this.
     `test_a_save_that_raises_after_an_extendable_exit_leaves_the_exit_and_the_next_resume_branches` (Task 11).
5. **The memory backend's slice and index agree with a full scan** (§5, "The memory backend"). Every in-process
   run, the `ThreadLauncher`'s default, reads through it, and an off-by-one in a slice is silent.
   `test_memory_reads_and_latest_agree_with_a_full_scan_at_every_cursor` (Task 2): every `after` from 0 to
   `last_seq() + 1`, with each filter and `limit` 0, 1 and none, and `latest(topic, name)`, after interleaved
   sends through two handles of one run.

### Task 2: The substrate: the memory backend's tail and index, and the substrate contract

**Interfaces:**
- Produces:
  ```python
  # runstate/channel/memory.py
  class MemoryLog:
      """One run's in-memory log, shared by every handle on it: the envelopes, contiguous
      from seq 1, a per-topic index of their positions, and one lock."""
      def __init__(self, envelopes: Sequence[Envelope]) -> None  # raises ValueError unless seqs are 1..N
  class MemoryChannel(Channel):
      def __init__(self, log: MemoryLog | None = None, *,
                   json_default: Callable[[object], object] | None = None) -> None
  ```
  `log=None` makes a fresh, private log (an exempt default: a new log, not a result). The registry in

### Task 3a: A format holds its tables

**Postgres suite:** yes.

**Why.** Open question 9: the migration store creates each destination with the live channel's DDL, so the

### Task 5: The condition algebra over counts

**Postgres suite:** no.

**Files:** create `runstate/_next/vocabulary/schedule.py`; `tests/test_next_schedule.py`.

**Interfaces:**
- Consumes: Task 4 (`Commits`, `Target`, `_MAX_COUNT`).
- Produces:
  ```python
  Condition = dict[str, Any]  # the wire dict of a schedule or stop trigger; only boundary functions take it

  class MalformedSchedule(ValueError): ...   # its message names the offending key by its path

  @dataclass(frozen=True) class Elapsed: seconds: float           # {time_seconds: s}; NaN refused
  @dataclass(frozen=True) class Fired:   n: int                   # {count: n}; only in until
  @dataclass(frozen=True) class AnyOf:   terms: tuple[Term, ...]  # non-empty
  @dataclass(frozen=True) class AllOf:   terms: tuple[Term, ...]  # non-empty
  Atom = Target | Elapsed | Fired          # Target is the lineage atom {stream, n} | {commits: n}
  Term = Target | Elapsed | Fired | AnyOf | AllOf

  @dataclass(frozen=True)
  class Schedule:
      from_: Term | None; every: Term | None; until: Term | None   # refuses a Fired outside until
      def atoms(self) -> Iterator[Atom]

  def parse_schedule(body: Condition, *, pure_demand: bool) -> Schedule   # raises MalformedSchedule
  def parse_stop_trigger(body: Condition) -> Term | None                  # None: no from, holds once drained

  class Coordinates(NamedTuple):
      """Counts at one node, its pending values included when it is the node being written (§3)."""
      streams: Mapping[str, int]   # count(X, node) per eager stream; an absent stream counts 0
      commits: int                 # count(Commits(), node)
      def of(self, x: str | Commits) -> int

  def satisfied(term: Term, *, at: Coordinates, time_seconds: float, count: int) -> bool

  class Decision(NamedTuple):
      fire: bool
      expired: bool

  class Subscription:
      """A registered schedule (§3, "Evaluation"). The claim holds registered_at, the fire
      count and the time of the last firing; the lineage supplies the count baselines."""
      def __init__(self, schedule: Schedule, *, registered_at: float, target: str | None) -> None
      schedule: Schedule             # read-only
      target: str | None             # read-only: the source it samples, None for a pure demand
      registered_at: float           # read-only
      lease: bool                    # read-only: is_lease(schedule)
      fires: int                     # read-only: the claim's firings (a Fired atom reads it)
      def evaluate(self, *, at: Coordinates, baseline: Coordinates | None, now: float,
                   valued: AbstractSet[str]) -> Decision   # valued: the sources whose registers hold a value

  def is_lease(schedule: Schedule) -> bool               # any Elapsed or Fired atom
  def references_time(schedule: Schedule) -> bool        # any Elapsed atom
  def unsatisfiable(schedule: Schedule, *, sources: frozenset[str]) -> str | None
  ```
- **The parse** converts the wire dict once, at the boundary, into the typed term, so nothing past it reads a
  string key: the grammar of subscription-v0.4 (`{stream, n}` takes exactly its two keys; n at most 2^53 - 1;
  `count` only in `until`), and with `pure_demand` also a `from`, an `every` or a `count` atom anywhere. A
  whole-number float and NaN are refused, though JSON Schema admits both. A fold that meets a logged body parses
  it first; a body that does not parse is malformed, never a lease, and the worker's `nak` spends it.
- Semantics, each from §3:
  - `from` and `until` hold once `count(X, node) >= n`; a `Target` reads `at.of(x)`; `Elapsed` reads
    `now - registered_at`; `Fired` reads `fires`.
  - `evaluate` checks `until` first. `every` is the delta rule against `baseline` for lineage atoms (the
    coordinates at the newest node on the lineage whose `fired` names the subscription, passed by the caller)
    and against the time of the last firing for a time atom; an atom with no baseline holds, so the first
    firing is immediate. A one-shot (no `every`) that fires expires at that node; an `until` that holds expires
    it, firing nothing. No interpolation inside a jump. A `{count: n}` `until` counts the firing at the node
    being written, so the nth firing's node expires it. The call is the firing: two calls at one node count two
    firings, and a caller that retries a write reuses the `Decision`.
  - The constructor takes the parsed schedule and the target, fixed at registration; `parse_schedule(body,
    pure_demand=target is None)` has already refused what the Worker naks as malformed. `evaluate` fires only
    when `target is not None and target in valued`; otherwise it evaluates only `until`, may expire, and moves
    neither `fires` nor the time baseline. A pure demand never consults `valued`.
  - `fires` and the time baseline are the claim's and only a lease reads them, since an `Elapsed` or a `Fired`
    atom is what makes a lease; a durable subscription reads neither, and nothing rebuilds them.
  - `unsatisfiable`: a progress atom naming a declared source, and an empty window (`from` implies `until` on
    one X: `until`'s n at most `from`'s), restated in counts from 0.3.0's corner check. An `until` that holds at
    registration is not refused (review §12, item 14). An absent `from` reads as `from` 0 on each X, so
    `{until: {commits: 0}}` is refused as `{from: {commits: 0}, until: {commits: 0}}` is. The target check (a
    subscription naming a non-source) is the Worker's, since it reads the envelope's `name`.

- **The drain** (§4, "A drain"), run first by `commit()` and `heartbeat()`: read `w`; read the

  `honored` reads. A withdrawal spends a pending stop that has not held. `rewind` leaves the decision alone.

- **`steps(until)`:** while the target is not reached at the position (`until.n <= count(until.x, position)`),
  yield `count(Commits(), position)`, then `commit()`; stop on a True decision. `ValueError` when `until.x` is a
  declared source (open question 1).

Each is left open by the spec or the brief. The controller adopted every recommendation on 2026-10-28, except
9 and 16, ruled as stated there, and amended the spec for 1, 4, 6 and 16. The owner's plan review (2026-10-30)
moved 9's seam out of the flip into its own Task 3a, on both backends, split Task 10, added the examples' smoke
test, and ruled 17, amending §6.

1. **A target naming a declared source** (§4, §5). It counts 0 forever, so `steps(until)` never ends and `ensure`
   re-drives while each chunk commits. *Recommended:* `steps()` raises `ValueError` before its first iteration,
   and `ensure` raises `ValueError` once its drive's claim declares the name a source.
2. **Where `Outcome` lives.** `Died.outcome` is a wire field, so the vocabulary needs the enum. *Recommended:*
   `vocabulary/payloads.py`, re-exported by `observables` and `runstate`.
3. **How `ensure_served` holds its `LiveDemand`** (§5). *Recommended:* a required keyword-only `demand: LiveDemand`
   the standing waker holds per run; a one-shot caller passes a fresh one.
4. **Folds with no head.** §5 says each fold is polled `fold.poll(ch, head)`, but demand and stops are by name for
   the whole log (§2). *Recommended:* `LiveDemand.poll(ch)` and `PendingStops.poll(ch)`, the first reading the
   latest head's closedness itself; only the stream folds and `Answers` take a head.
5. **The server identity in the stamp** (§11). It must tell the writing server from a standby and a promoted
   standby. *Recommended:* `system_identifier` (`pg_control_system()`) and the timeline (`pg_control_checkpoint()`),
   with the probe abstaining on a mismatch or when `pg_is_in_recovery()`. Task 3b verifies a non-superuser can
   read them, and returns to the owner if not.
   *Amended (owner, 2026-10-30):* the timeline is the live WAL insertion timeline,
   `(pg_split_walfile_name(pg_walfile_name(pg_current_wal_lsn()))).timeline_id`, computed per row inside `_CAS`
   and `_UNCONDITIONAL`, so a stamp is always the timeline its row was written on; the key stays per
   connection, and the open no longer reads the identity. The probe reads `CASE WHEN pg_is_in_recovery() THEN
   NULL ELSE <identity> END` at each call. **PostgreSQL 16 is the floor** (`pg_split_walfile_name` arrived in
   16; CI runs `postgres:16`). *Why:* batch 2's review reproduced the recommended source's hole on PostgreSQL
   18.4 with a streaming standby and `pg_promote(true)`: since PostgreSQL 13 a promotion requests only a spread
   checkpoint, so `pg_control_checkpoint()`'s timeline stayed the old one for more than 100 s after it, a
   channel on the promoted server reported the old identity, `session_ended` returned `True` for a writer alive
   on the old primary, and a connection opened in that window would have stamped the old timeline for life. A
   channel opened in recovery is not refused, which would kill long-lived observers and workers across a
   failover. *Revival trigger:* a consumer on PostgreSQL 15 or older; then a parse of the WAL file name's first
   8 hex digits, as a Strategy resolved at the open, gives the same integer.
6. **Who kills an orphan** (§3: "a launcher there kills such an orphan rather than launch a successor beside it").
   Killing by pid is unsafe while pid reuse fools the probe (§12). *Recommended:* only `LocalLauncher.reap()`,
   for a live child of its own whose claim a death report ended, through its `Popen`; the deciders never kill.
   The orphan cannot write meanwhile, since its session is gone.
7. **The 0.3.0 reads that the corpus runner and the 0.2.0 → 0.3.0 step's tests compare against.** *Recommended:*
   a frozen copy at `scripts/reads_v0_3_0.py` (Task 1), retained like a step. I1's half that needs a 0.3.0 Worker
   is dropped; its demand half stays.
8. **The staging package** `runstate/_next/` and `tests/test_next_*.py` (Architecture). *Recommended:* yes; the
   alternative is red intermediate commits.
9. **`stores.py` builds a migration's Postgres destination with the live `_CREATE_TABLE`**, so after the flip a
   0.2.0 → 0.3.0 migration would create a 0.3.0 table with 0.4.0's stamp columns. *Ruled (controller,
   2026-10-28):* do not accept it. A format holds its layout, and the stamp is the first change to a format's
   table, so the Postgres DDL joins the `Layout` Protocol (`pg_ddl`), and the channel and the migration store
   each take it from the format they write. *Amended (owner, 2026-10-30):* the seam lands in Task 3a, just
   before the stamp that needs it, so the flip only moves the stamped table from 0.3.0's layout to 0.4.0's
   (Task 24) and keeps to the format change. The owner folded in the SQLite twin the same day (`stores.py` took its SQLite
   destination's schema from `channel/sqlite.py`'s `_SCHEMA`): a format holds its tables on both backends.
   `stores.py` leaves the frozen list for that one edit; the step modules stay frozen. On the branch before
   Task 24, 0.3.0's layout holds the stamped Postgres table, which master never sees.
10. **`MostProgress`'s tie-break** (§6). *Recommended:* the higher node seq.
11. **`lineage.py`'s public `lineage` and `count`.** §5 names neither. *Recommended:* private in `observables`;
    the runner uses `prefix_len` at `AtNode` and `LatestClaimHead`.
12. **The evidence of an exit 0 and of a thread's return or raise** (§3). *Recommended:* `reap: exit 0`,
    `reap: returned`, `reap: <ExceptionType>: <message>`.
13. **Result-changing defaults on touched signatures** (code rule 7). *Recommended:* `Watcher`'s
    `heartbeat_timeout` and `sweep`'s `resume`, `stop_on_failure` and `watcher` become required; the launchers'
    `backend` keeps its default.
14. **`worker_completed`'s argument** (§5: "the head is closed"). *Recommended:* it keeps taking a `RunResult`:
    tier `EXIT` and outcomes `{COMPLETED}`.
15. **`RecordlessExitError`'s fixed point** (§5). *Recommended:* the second consecutive recordless drive at an
    unchanged head and `Commits()` count raises; the first re-drives.
16. **The Watcher's session tier** (§5 lists `episode_lock_released`), though §11 deletes the episode lock.
    *Ruled (controller, 2026-10-28):* rename it `session_ended`, after the evidence it rests on, and amend §5;
    a name that names a deleted mechanism misleads every reader of a verdict.
17. **A save that raises after an extendable exit landed** (§6). The commit case ends the claim, so its exit
    records it; at the exit the claim has already ended. *Ruled (owner, 2026-10-30):* it propagates, the exit
    stands with its own verdict, nothing more is written, and the next claim branches from an older checkpoint.
    Not an expedient: whether a node has a checkpoint is the store's fact, never the log's, and each way of
    recording the failure fails the rubric (a pre-CAS save names a seq it may not get; a post-exit record speaks
    for an ended claim, and a death report defers to a readable exit; a record of saves duplicates the store). The process's failure stays on
    the external plane, in `supervisor.terminated`'s exit code. §6 amended; Review Focus 4 and Task 11 pin it.

## Spec defects found

- **§3, "Who writes a death report":** "a launcher there kills such an orphan" names no launcher and no
  mechanism, and a kill by pid contradicts §12's pid-reuse limit (open question 6).
- **§5, `ensure`, and §4, `steps(until)`:** nothing covers a target naming a declared source, which counts 0
  forever and drives without end (open question 1).
- **§5, "Bounded reads":** "each is ... polled with `fold.poll(ch, head)`" does not fit `LiveDemand` and
  `pending_stops`, which §2 makes by name for the whole log (open question 4).
- **§5's `Tier.episode_lock_released`** names the mechanism §11 deletes (open question 16; amended).
- **§6, "Save":** nothing says what a save that raises does, at a commit or at an exit (open question 17;
  amended).
- **§3, "Evaluation" and the refusals** (found implementing Task 5; amended, controller, 2026-10-30):
  - `Subscription.evaluate` as Task 5 first specified it cannot know a pure demand, which never fires, or a
    source with no value yet, which does not fire but may expire. A subscription's target is fixed at
    registration, so it is a constructor argument; which sources hold a value varies per call, so it is
    `evaluate`'s.
  - Two spellings of one schedule got opposite answers: `{until: {commits: 0}}` was accepted and
    `{from: {commits: 0}, until: {commits: 0}}` refused. The empty-window check reads an absent `from` as
    `from` 0.
  - Nothing said whether a `{count: n}` `until` counts the firing at the node being written. It does.
- **§5, the folds and the answer fold** (found implementing Tasks 7–8; amended, controller, 2026-10-30):
  - "Incremental equals pure" listed only the duplicate-seq check as the pure walk's alone; a fold now raises
    wherever its pure read does but there, the non-value check included.
  - Nothing said whether an unparseable subscribe is live demand. It is, until a `nak` names it, as a
    malformed stop is pending until its `nak`; otherwise no worker is launched to refuse it.
  - `live_demand`'s `ended` called the full verdict, so an old claim's contradictory exits raised forever in
    the pure read while its fold answered. `ended` is presence-based and never raises.
  - A subscription's class and target are its first send's, so a void lease cannot come back as demand.
- **§11, `channel-postgres.md`, against `log-formats.md` §3:** the stamp columns are a layout change of the current
  format that reaches an older format's destination table, because the frozen `stores.py` takes its DDL from the
  live channel (open question 9).
